## 0. 先講結論：兩個缺陷實際上出在哪裡

回去看了原始程式碼（`建立RAG.py`、`使用llm擴充資料.py`），比 09-13/09-14 報告
記錄的更具體：

### 0.1 資料洩漏的根源

`建立RAG.py` 把**每一筆語料**都寫成：

```python
rag_corpus = [f"{row['statement']} true_label is {row['status']}" for _, row in rag_df.iterrows()]
```

這件事本身不是問題（RAG 用帶標籤範例做檢索本來就是這樣設計）。**問題是語料庫的
來源 `rag_df` 從未和 test set 做互斥切分**——`使用llm擴充資料.py` 是對整份
CSV `sample(frac=1, random_state=42)` 取樣，沒有先扣掉 test set 再建語料庫。
`test.py`／`prompt最佳化.py` 各自獨立切了一次 test set，兩邊的切分沒有互相對齊，
於是 134 筆 test 原文連同 `true_label is X` 一起躺在語料庫裡，等於考卷答案被
放進題庫。R1FIX 的「剔除法」只是把這 134 筆從**評估集**剔除，語料庫本身**沒有
清乾淨**——如果留在題庫裡的其他語料庫項目和某個 test_clean 樣本高度相似（近似
重複但沒到 0.95 門檻），檢索仍可能撈到「答案就寫在旁邊」的鄰居，只是沒被目前的
稽核抓到。**完整重作必須從根本保證：語料庫的來源池與 val/test 三個集合互斥，
而不是切完之後才去比對剔除。**

### 0.2 輸入截斷的根源

`使用llm擴充資料.py` 呼叫 `ollama.chat` 時只給了 `temperature`，沒有給
`num_ctx`；`建立RAG.py` 的 `SentenceTransformer.encode()` 同樣沒有指定
max sequence length。兩者都吃 Ollama／sentence-transformers 的預設值（2048 /
通常 256 個 token），**長文件會被靜默截斷**而不是報錯——這代表：

- 擴增資料的「改寫」可能只看到原文前面一截就動筆，改寫文本與原意不一致；
- 建語料庫的向量本身可能只編碼了長文件的前半段，檢索出來的「相似鄰居」失準；
- （原推論流程 `test.py`／`prompt最佳化.py` 同樣沒設，最終輸出的分類判斷也可能
  是基於被截斷的輸入做的）。

`revision/00_env_probe.py` 已經對**新流程**強制要求明確指定 `num_ctx` 並在
`05_metrics.py`／`09_verify_all.py` 斷言未觸頂，但這只保護了 R1FIX 這次「重跑
的五條件＋擴增稽核」步驟，**語料庫與擴增資料本身仍是用舊流程（未設 num_ctx）
產生後直接沿用**（`revision/README.md`：「不重建資料集、不重建索引、不重新
生成擴增資料」）。完整重作必須連語料庫建構、擴增生成這兩步都重跑一次，
全程掛 `num_ctx` 斷言。

## 1. 要不要 fork？我的建議

**建議：兩層都 fork，理由如下。**

### 1.1 Git 層：開新分支（或用 worktree 平行工作）

- `main` 目前的狀態（`revision/` + `runs/R1FIX/`）是 9/21／9/25 回覆信要引用的
  數字來源，任何後續操作都不該有機會弄壞它。
- 完整重作會跑很久（重建語料庫、重新生成 17,772+ 筆擴增文本、五條件 × 1,700
  重新推論……規模不小於甚至大於 R1FIX），過程中必然會經歷「跑壞、改腳本、
  再跑」的反覆，不適合直接在 `main` 上進行。
- 做法：從 `main` 切一個新分支（例如 `rebuild-v2`），用 `EnterWorktree` 開一個
  獨立工作樹進行，兩邊互不干擾；回覆信如果之後还要修，可以直接切回 `main`，
  不受重作進度影響。

### 1.2 目錄結構層：另開新目錄，不動 `revision/`

- `revision/` 這個目錄的設計前提就是「剔除而非重建」——它的存在意義是最小改動
  滿足審稿人，如果直接在裡面改成「真的重建語料庫」，會讓「這批數字是給審稿人
  的回覆」還是「這批數字是新論文的」變得模糊，回頭要查對哪個數字對應哪封回覆信
  會很痛苦。
- 沿用專案已有的先例——`revision/README.md` 開頭就寫「原始腳本保持不動作為
  對照，本目錄是獨立的一套流程」——這次應該比照辦理：新增一個目錄（暫定
  `rebuild/`，也可以你決定要不要改名字），`revision/` 完全保持不動繼續作為
  回覆信的證據，`rebuild/` 是重新設計過、真正解決兩個根源缺陷的完整流程。
- `rebuild/` 可以重用 `revision/common.py` 裡已經修好、且不涉及「剔除法」假設
  的通用邏輯（label parser、JSONL 逐筆存檔、num_ctx 斷言、faiss 中文檔名處理），
  不用重寫這些已驗證過的部分。

兩層都做的好處：即使之後決定重作結果需要放棄、或指導教授要求換方向，`main` +
`revision/` 這條回覆信用的證據鏈完全不受影響，可以隨時獨立檢視、獨立回退。

## 2. 需要重作的實驗 Case 清單

分成「前置重建」與「正式實驗 Case」兩段。前置重建不是一個「條件」，但沒做完
後面所有 Case 的數字都不可信；正式 Case 沿用原論文/R1FIX 已建立的 C1–C5 命名，
確保這次重作跟既有報告、回覆信的代號可以對得起來。

### 2.1 前置重建（跑實驗前必須先做，且必須互相驗證乾淨）

| # | 項目 | 目的 | 驗收方式 |
|---|---|---|---|
| P1 | **三向切分先行**：先從全量資料切出 train pool / val / test 三個互斥集合，並用 hash + embedding 近似重複掃描（沿用 `01_build_eval_set.py` 的 ≥0.90/0.95 邏輯）雙重驗證三者兩兩之間相似度都在門檻以下 | 從根本避免 §0.1 的洩漏成因 | `exclusion_report.json` 等價物：三集合逐一交叉比對，0 筆逐字重複、近似重複數量與最大相似度需列出 |
| P2 | **語料庫重建**：只從 P1 切出的 train pool 建 `rag_corpus`／FAISS index，`SentenceTransformer.encode()` 明確指定 max_seq_length，超長文件斷言不截斷 | 解決 §0.1（來源池已排除 val/test）與 §0.2（corpus 端截斷） | 語料庫全文與 val/test 集合做一次全量近似重複掃描，需為 0（不是抽樣） |
| P3 | **擴增資料重新生成**：重新對 train pool 呼叫 LLM 改寫，明確指定 `num_ctx`（依原文長度分布訂一個安全值，需大於 corpus 中最長文件的 token 數），並沿用 `revision/02_aug_audit.py` 的樣板率／標籤詞率稽核 | 解決 §0.2（擴增端截斷），並延續已知的「改寫文字直接嵌類別詞」問題稽核 | `aug_audit.json` 等價物：0 筆因 num_ctx 被截斷；樣板率／標籤詞率需重新量測（不假設跟舊資料一樣） |

> P1–P3 的順序不可顛倒：P2/P3 都依賴 P1 先切好的互斥集合，否則語料庫又會
> 重蹈「先建語料庫、再切 test」的覆轍。
